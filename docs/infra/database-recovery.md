# 已有数据库与迁移分支兼容

环境初始化现在明确区分两种模式：

- `DATABASE_MODE=compose`（默认）：由本项目管理 Docker PostgreSQL。首次启动会在拉取镜像前检查 `127.0.0.1:POSTGRES_PORT`；端口被其他服务占用时快速退出。已有本项目容器可重复启动。新建实例时须同时修改 `POSTGRES_PORT` 和 `DATABASE_URL` 的端口。
- `DATABASE_MODE=external`：复用本机或已部署的 PostgreSQL，只验证 `DATABASE_URL` 连接，不拉取镜像、不创建/停止容器，也不需要把业务角色当成数据库管理员。`db:down` 在此模式不会停止外部数据库。

已有 `.env` 不会被 `env:setup` 覆盖。通过修改文件显式选择模式，然后运行：

```sh
npm run env:setup
npm run db:status
npm run db:migrate
npm run db:check
```

## 已发布人工审核分支

本项目保留原 `0000`—`0006` SQL，不通过删除迁移记录、替换旧哈希、重置数据卷或跳过全部校验来处理不匹配。

当数据库包含已发布 `0005_manual_editorial`（时间 `1793351546786`、原始 SHA-256 `05484f8b…`），迁移入口选择专用的兼容路径：共同 `0000`—`0004` → 原始人工审核迁移 → `compat/0006_legacy_workflow_bridge.sql`。原先已登记的独立审核分支 `e615920d… / 1793328115377` 在核对其结构与保护触发器后原样保留。只有完整哈希和时间同时匹配才识别；其他记录仍拒绝升级。

升级前在同一事务锁定旧分支受管表，逐项比较从原始 SQL 在独立库生成的字段、默认值、索引、约束、触发器和函数核对文件。只接受精确已知的备份恢复等价表达式。当前兼容路径要求旧任务没有在途执行、旧审核/裁决/批准记录或未清理的批准引用；存在这些数据时停止，要求专门转换，避免隐藏历史或改变资格。

新审核数据使用 `workflow_review_cycles`、`workflow_manual_decisions` 和任务的 `workflow_review_cycle_id`，保留旧分支同名表与旧字段。升级只追加实际执行的兼容增量记录，旧记录 ID、哈希和时间不变；不会把未执行的主线 `0005/0006/0007` 伪登记为已执行。

干净库或原主线安装继续执行正常迁移；新增 `0007_workflow_namespace.sql` 将已经存在的新审核表及引用重命名到独立名称，保留其行和关联。主线和兼容分支最终使用同一套应用表名。
