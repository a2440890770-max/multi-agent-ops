# 人工编辑、版本、审核与批准验收

当前真实入口：`http://127.0.0.1:5173/tasks`。两个独立浏览器分别登录同一 `admin`，打开同一个任务详情网址。全程不需要 Agent；不用启动“模拟执行”或生成澄清问题。

## 1. 创建、编辑、保存与自批

1. 点击“创建任务”，填写标题和要求，保存进入详情。
2. 点击详情右上角“编辑与审核”，在“人工文案编辑 → 文案内容”填写：`欢迎了解本次产品介绍，详情以官方说明为准。`
3. 点击“保存新版本”。在“文案版本历史”确认 V1、版本编号、无父版本、SHA-256 摘要。
4. 点击“提交基础审核”。“审核问题与阻断项”应显示通过。
5. 使用当前创建者账号点击“批准当前版本”。审批状态应成为“已批准”，批准人是当前创建者。
6. 刷新页面：正文、历史、审核与批准状态仍存在。

## 2. 不可变版本与历史比较

1. 在 V1 末尾添加 `欢迎查看参考资料。`，点击“保存新版本”。
2. 历史出现 V2，父版本编号等于 V1 编号；V1 正文和摘要不变，V2 有新摘要。
3. 点击“查看 V1”，再点击“比较所选版本与当前版本”，应显示新增文字。
4. 查看“当前版本预览”：仍为 V2，浏览历史不会切换当前版本。
5. 旧批准应显示失效；需要对 V2 重新审核和批准。

摘要是完整正文 UTF-8 字节的 SHA-256，保留原始空格和换行。自动化验收同时检查数据库拒绝更新/删除历史版本、审核和裁决记录。

## 3. 双浏览器编辑冲突

1. A、B 都打开同一个已保存版本，点击“刷新详情”。
2. B 输入 `B 尚未保存的文案。`，不要保存。
3. A 修改并保存为新版本。
4. B 不刷新，点击“保存新版本”。B 的 Network 中 `content-versions` POST 应返回 409。
5. B 自动显示“服务器当前版本”和“我的未保存输入”，两份文字都保留。
6. B 刷新，自己的草稿仍存在。
7. 核对差异后，点击“比较当前版本与我的输入”，再点击“保留输入并使用当前版本为基础”。
8. B 明确点击保存，产生另一个新版本，父版本是 A 保存的版本；A 的版本仍保留。

相同的过期版本保护也应用于提交审核、裁决和批准。只看到提示不足以判定通过，应确认 HTTP 409 且没有覆盖新记录。

## 4. 确定性阻断不能裁决绕过

默认禁止词：`全网最低`、`100%有效`；另检查最多 280 个 Unicode 字符和不含 HTML 标签。

1. 保存 `这是全网最低的产品介绍。`，提交基础审核。
2. 出现“确定性阻断”，批准按钮不可用，不显示可放行的主观裁决入口。
3. 即使直接向裁决接口发送“管理员同意放行”，服务端也必须返回 409 `REVIEW_BLOCKED`；批准请求同样被拒绝。
4. 删除禁止词，保存新版本，再审核，方可批准。
5. 分别以 281 字符文案、`<b>产品介绍</b>` 重复测试，同样被阻断。

账号配置可在“管理设置 → 基础规则与版本”修改；禁止事项每行一个明确词语，采用字符匹配，不冒充语义或事实核验。

## 5. 主观裁决与理由

1. 保存一条无确定性阻断的文案。
2. 在“主观审核意见”填写 `语气是否应更活泼，需要人工判断。`，提交基础审核。
3. 应显示主观意见，并出现“裁决结果”“裁决理由”“保存人工裁决”。
4. 理由为空或仅空格时提交，必须被拒绝；服务端同样拒绝空白理由。
5. 选择“仍需修改”，填写理由并保存：记录保留，仍不能批准。
6. 选择“接受上述主观分歧”，填写明确理由并保存：无其他阻断时可以批准。
7. 刷新，在“审核与裁决历史”看到两条裁决、各自理由、裁决人和时间，原审核意见不被改写。

## 6. 配置、新执行与批准失效

- 已批准后修改文案：新版本使旧批准失效。
- 已批准后启动新的模拟执行：旧批准立即失效，即使新执行未完成也不能沿用。
- 在管理设置修改简介、语气或禁止事项并填写原因保存：配置版本增加，旧批准失效，必须按新配置重审。
- 直接携带旧批准编号、旧版本和旧摘要请求发布，服务端拒绝，不创建发送记录。

真实发布通道尚未接入。有效批准也不会实际发微博；因此“发布按钮不可用”不能单独证明旧批准拦截，须检查服务端拒绝结果。
