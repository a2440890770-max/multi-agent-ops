# D6：目标账号登记、人工交接与结果回填

本批实现管理员登记团队唯一目标微博账号、批准后的确认面板，以及显式确认后创建人工交接记录并冻结文案。打开面板仍为只读；创建交接后状态为“待人工发布”，不会向微博发送请求，也不会视为发布成功。冻结后支持原文复制和人工发布指引，并可回填、人工核实发布结果。系统不代替操作人登录微博、发布或自动抓取平台证据。

## 使用方法

1. 更新代码并安装依赖，备份已有业务库，执行 `npm run db:migrate`。本批新增 `0006_d6_account_registration.sql` 至 `0009_d6_manual_publication_retry.sql`，不覆盖 D5 的历史迁移。
2. 管理员登录，进入“管理设置 → 目标账号与授权”。
3. 填写昵称、`https://weibo.com/u/<UID>` 主页链接或数字 UID，按实际权限启用人工操作资格并勾选确认，填写登记原因后保存。
4. 回到任务详情，人工保存文案、完成基础审核和必要主观裁决，再批准当前版本。
5. 点击批准区的“人工发布交接”。页面再次从后端核对资格，展示目标账号、主页、批准版本和原样正文，核对后点击“确认创建交接并冻结文案”。交接保存账号、原文、SHA-256、批准记录、配置版本、操作人和时间；刷新后仍可查看。

6. 交接记录创建后点击“复制冻结文案”，按人工发布指引自行核对登录账号、粘贴并核对原文、手动发布，发布后保存该条微博的链接。若自动复制失败，可点击“选中全文手动复制”，使用系统复制快捷键或菜单。

复制仅在待人工发布的人工交接中提供，来源为交接冻结快照，保留原始空格和换行，不包含指引或账号资料。打开只读确认面板时不提供复制按钮；复制不调用写入接口，不新建发送，不改变交接状态。刷新后仍可查看指引并再次复制，之前的复制成功提示不会保留。手动发布后应回填单条链接、实际账号 UID 和完整实际正文，避免重复发布；实际内容有差异时不能视为批准版发布成功。

账号信息由管理员保存到数据库，不在源码中预置任何真实账号。首次将占位账号登记为真实账号、更换 UID 或停用人工操作资格时，相关旧批准失效，清空当前审核引用；必须重新审核批准。改名不更换 UID 时保留批准，但更新任务 revision，要求已打开的确认页面重新核对。

人工操作资格独立于 `authorizationStatus` 与 `officialPublishAvailable`，登记不会伪造官方 API 授权。已有官方凭据或有效官方授权的账号不能直接更换 UID，以免错误关联旧凭据。

## 接口

- `GET /api/v1/account-registration`：读取同团队的公开目标账号信息及登记人/时间；不存在账号时返回 `account=null`。
- `PUT /api/v1/account-registration`：仅管理员，使用 `expectedVersion`、`Idempotency-Key`、同源 Origin 和 CSRF token 防止并发覆盖和重复登记。
- `GET /api/v1/tasks/:taskId/manual-publication-entry`：只读核对批准、文案摘要、账号、配置和审核；不改变业务状态。

- `POST /api/v1/tasks/:taskId/publications`：复用已有发布契约，`channel=manual`，传当前 `expectedRevision`、`accountId`、`contentVersionId`、`contentHash`、`approvalId` 及 `Idempotency-Key`；返回 202 与稳定的 operationId 和 dispatchId。
- `GET /api/v1/tasks/:taskId/publications`：同团队任务的交接历史，支持游标分页。
- `GET /api/v1/tasks/:taskId/publications/:operationId`：读取原操作、冻结快照与当前任务；网络超时优先查询此记录或任务详情。

`actions.manual_publish_entry` 表示可打开只读面板，`actions.publish` 表示具备创建人工交接的资格。创建后两个动作都被锁定；不会调用官方发布接口。相同版本与账号永久复用原操作，不因 HTTP 键不同或过期而新增发送。

冻结快照包含公开账号资料、完整批准记录和正文，不含凭据。创建交接、首次人工发送记录、任务锁、审计和幂等结果在同一事务提交。后台阻止改稿、审核、批准、执行及相关账号登记/配置变更；数据库触发器阻止修改或删除快照及发送身份绑定。明确未发布、填写原因并确认原交接已停止且不会继续发布后，结束本次交接并解除锁定；不能通过关闭页面、等待或接口超时解锁。明确未发布后，如原文案、审核、批准、账号与配置仍有效，可以同版本重新交接；也可编辑保存新版本后重新审核批准。原交接和核实历史保留。

## 验收重点

- 管理员可保存登记，刷新后恢复，运营人员无法写入；接口不返回凭据。
- UID 与主页输入拒绝外站、非 HTTPS 链接或无效 UID；昵称和原因不能仅为空白。
- 人工操作启用前必须确认操作资格；不会自动开通官方 API 发布。
- 同版本并发登记只允许一人保存；相同请求标识重放不重复写入；响应丢失后刷新仍可确认原请求。
- 首次登记、更换 UID、停用资格使旧批准失效，不能跳过重新审核。
- 无有效批准、模拟产出、工作中、账号未登记或资格未启用时入口禁用并说明原因。
- 有本地未保存修改或编辑审核请求尚未确认时入口禁用。
- 已打开页面的旧入口再次点击时，后端仍重新检查，不能凭旧页面预览失效批准。
- 确认面板保持批准正文的原始空格和换行；打开、关闭和刷新不创建交接记录、不持有发布锁、不改变发布状态；只有显式确认创建后才冻结。

- 创建交接时重新核对账号、版本、批准、审核配置和任务 revision，拒绝失效页面和篡改参数。
- 交接后冻结正文保留空格及换行，显示账号主页、版本、摘要、批准人、操作人、时间、操作及发送编号；发布状态为待人工发布，任务生命周期保持开放。
- 并发/重复提交、不同键、键过期或服务重启均复用原交接；刷新不自动提交 POST。
- 已提交响应丢失时刷新读取原交接；提交前断网时保留原请求与键，允许显式确认。审计失败时全部回滚。
- 冻结后 API 直接修改也返回 `423 PUBLICATION_LOCKED`；查询失败不会解除锁或重建发送。

- 冻结后复制内容等于批准原文，保留空格和换行；确认面板中不允许复制。
- 剪贴板拒绝或不可用时明确显示失败，支持选中全部冻结原文手动复制；选中全文不显示复制成功。
- 发布指引展示冻结账号昵称及 UID，引导自行核对、粘贴、检查、发布并保存链接；引导回填结果及内容不一致的处理。
- 复制和查看指引不修改任务、审计或发送记录，刷新后仍可操作；桌面和移动端均无横向溢出。

## 回填与人工核实

1. 在“人工发布交接记录”下填写“回填发布结果”，提交微博单条链接、实际发布账号 UID、完整实际正文及核对说明，由当前有权限的操作人确认。
2. `POST /api/v1/tasks/:taskId/publications/:operationId/backfills` 复用原契约，绑定当前 dispatchId、冻结账号/版本和 expectedRevision。新增 observedAccountUid、observedBody、manualConfirmed；实际摘要由服务端计算，不能只用客户端声称的摘要证明一致。evidenceIds 可为空，人工观察和说明本身作为证据保存；非空引用须来自本任务。
3. 支持 `https://weibo.com/<UID>/<微博标识>`、`https://www.weibo.com/<UID>/<微博标识>` 和 `https://m.weibo.cn/detail/<微博标识>` / `status/<微博标识>`。拒绝主页、非 HTTPS、外站、账号密码或端口链接；去除查询参数及片段。桌面链接中 UID 也须与冻结账号一致，移动链接则依据操作人填写并确认的实际 UID 核对。
4. 账号、正文（包括空格换行）和链接均匹配且 manualConfirmed=true，才进入已发布并终结任务。确认方式始终为 manual，不冒充官方接口确认。
5. 有差异、缺少确认或结果不确定则进入待核实，保存观察原文、服务端摘要、实际 UID、链接、说明、自动差异、操作人和时间，继续锁定。通过 `POST /api/v1/tasks/:taskId/publications/:operationId/verifications` 追加核实；历史证据不可编辑删除。
6. 明确未发布须填写原因，同时确认 manualConfirmed=true 和 previousDispatchFenced=true。结束本次交接后状态为 failed、任务仍开放、活动锁释放，可编辑并保存新版本。声明未发布却同时提供发布观察资料时有歧义，仍进入待核实。
7. 已发布后可补充人工核实记录；矛盾证据单独登记，保留原成功事实及原成功链接，不解锁、不补发。旧失败交接的新回填不能修改新版本的活动交接。
8. 回填、状态、任务锁、审计和幂等结果在同一事务保存。重复请求、不同 HTTP 键或键过期都不重复保存同一操作人的同一次证据。断网时保存原输入和原键，刷新先查询，查不到原记录才显式确认原请求，不自动 POST。

本批自动化验收使用合成数据。D6/M1 中的真实人工发布验收，仍须由有权限的人员实际发布一条已批准测试文案，再回填并核对账号、内容、单条链接，不能由模拟测试替代。

## 同版本失败后重新交接

- 失败交接记录显示“重新人工交接”。先通过已有 GET 操作详情核对最新任务和资格，再展示账号、原批准正文、原操作及上次发送编号、上次未发布原因；填写本次原因后明确确认。打开或关闭面板均不创建发送、不占锁。
- `POST /api/v1/tasks/:taskId/publications/:operationId/retries` 实现已有契约，目前仅支持 channel=manual。原操作与当前发送必须为 failed，且当前发送有明确未发布、人工确认和停止原交接的持久化证据；正文、原审核、原批准、配置和账号资格仍有效，无其他工作或发布锁。
- 文案、审核、批准已变化，或账号/配置变更使原资格失效，拒绝旧版本重交接；不提供恢复旧稿流程。本地未保存输入或编辑审核请求尚未确认时也禁用入口。
- 同一 operationId 新增递增 dispatchNo，保存 previousDispatchId、本次原因、操作人和时间；原快照、首次交接时间、旧发送及核实记录不变。任务重新持有原操作的发布锁，进入待人工发布，随后仍使用复制指引和正常回填入口；不调用微博 API。
- 每个原发送最多有一个后继发送，数据库唯一键及同操作外键保证此身份永久稳定。并发、重复点击、换 Idempotency-Key、键过期和之后再次失败都不能使旧请求新增发送；只有以最新失败发送为前次 ID 的新动作，才可能再增加一条。
- 发送、操作当前指针、任务锁、审计与幂等结果同事务提交。审计失败全部回滚；网络结果不明时保留原请求及键，刷新后先查询，再显式确认，绝不自动 POST。
- 发送历史展示每次状态、编号、前次发送、原因、操作人和时间。旧发送的迟到回填不能改写当前新发送结果。
