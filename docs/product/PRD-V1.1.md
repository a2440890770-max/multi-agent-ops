## 1. 背景、目标与成功定义

项目面向内部运营团队，以“每天从 GitHub 热榜中选一个项目，在抖音进行图文解读”为真实任务场景，构建可协作、可追溯、有长期记忆并能提出改进建议的 Agent 系统。账号内容不局限于 AI 项目；重点是说明项目解决什么问题、适合谁、有什么已知条件或限制，并保留原始来源。

目标优先级沿用 V1.0：验证多 Agent 相对单 Agent 的效果、长期记忆的跨任务复用价值、反思与策略优化的可重复收益，再提升内容生产效率。不得以“实验必须证明多 Agent 更优”作为验收条件，也不能只凭 Agent 自评分证明效果。

| 验收类型 | 第一阶段成功定义                                                                                                                          |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 功能验收 | 从任务创建、热榜热榜候选展示、人工选择、深入研究到图文策划、审核批准、成品图片准备、浏览器发布和记录形成闭环                              |
| 发布验收 | 浏览器在正确账号上传已确认图片和文案，提交后核实单条内容链接/可用标识及平台显示状态；人工核实与自动核实分别标记，不把点击成功视为发布成功 |
| 研究验收 | 在冻结候选、选中项目、资料和预算等条件下完成单/多 Agent 对照，报告质量、修改量、耗时、成本、失败样本及限制                                |

“每日一个”是运营计划目标；无候选、资料不足、未选项目或未获批准时允许当天不产出。首期不保证无人值守日更，不以曝光、互动增长或视频质量作为必须达成的指标。

## 2. 已确认范围与权限

### 2.1 第一阶段范围

- 一个内部团队、一个抖音账号，团队内共享业务数据；不开发外部多租户产品。
- 通过 XXAPI 获取当次 GitHub 热榜快照，只展示返回的项目名称、描述和链接，由用户选定一个后开展资料搜索与分析。
- 首期支持手动创建和启动任务；“每日内容”不自动承诺定时创建、定时抓榜或定时发布。自动触发时间和频率未另行确认，定时能力作为后续计划。
- 一次任务围绕一个选定项目产出一份图文策划包，包含标题、正文、逐页文案、画面建议、项目链接、来源和必要警告。
- 首期人工制作最终图片；系统通过浏览器自动化上传图文并发布，不自动生成图片或视频，不负责录音配音、剪辑或渲染。
- 发布优先使用浏览器自动化，先验证真实账号和图文流程；若不可行，再评估 API 的能力、权限和成本，不在运行中自动切换发布通道。
- 固定 Supervisor、Research、Content、Review 四个核心 Agent，另有手动复盘；不提供任意 Agent 创建器。
- Supervisor 采用 Claude Agent SDK 原生子 Agent 分派，D9 先接 Research；后续工具按阶段开放。Supervisor 不直接搜索或读取网页/文件。
- 热榜获取和选中项目研究分阶段授权：启动时只抓榜并等待选择；“选定并深入研究”才授权一轮选中项目研究，每轮补充研究需用户另行授权。技术重试不产生新授权。
- 用户点击“选定并深入研究”明确选中项目并授权深入研究；该动作不是内容批准或发布授权。
- 初稿后最多自动修改三次，仍不通过转人工；候选数量不足时不凑数、不自动加入榜外项目；没有可用项目则等待人工处理。
- 人工批准具体图文策划版本，可批准自己创建的内容；人工制作图片并上传系统，确认完整预览后另行点击“发布”，系统才执行浏览器自动化。批准本身不自动触发发布。
- 记忆分层治理、手动复盘、离线评测、来源追溯及权限隔离继续保留；候选经验不自动成为正式策略。

### 2.2 角色权限

| 操作                                                             | 管理员 | 运营人员     |
| ---------------------------------------------------------------- | ------ | ------------ |
| 登录、查看团队任务、候选、研究及执行历史                         | 是     | 是           |
| 创建任务、答复澄清、选择项目并授权研究、停止执行、终止与人工重试 | 是     | 是           |
| 编辑可编辑策划、提交审核、裁决主观意见、批准具体版本             | 是     | 是           |
| 准备成品图片、确认发布、处理浏览器登录及核实发布结果             | 是     | 是           |
| 手动复盘、业务记忆治理、运行已配置实验及人工评分                 | 是     | 是，保留记录 |
| 管理成员、目标账号、供应商配置、工具与规则版本                   | 是     | 否           |
| 在界面明文查看 API Key 或平台凭据                                | 否     | 否           |

后端必须验证角色、团队、目标版本和实际授权，不能只隐藏前端按钮。业务系统 Session、Cookie 与安全细节沿用[技术选型](../architecture/stack-decisions.md)。浏览器发布须绑定实际抖音登录账号，平台登录态隔离存放，不向 Agent、前端业务响应或 Trace 暴露 Cookie；账号登记或浏览器登录不等于获得官方 API 权限。

## 3. 业务主流程与人工节点

### 3.1 主流程

```text
手动创建/启动任务
  → Supervisor 判断要求；必要时澄清
  → 获取热榜快照并展示 API 项目列表；不逐个分析候选
  → 等待用户选择项目
  → 用户点击“选定并深入研究”，保存选择并产生新的研究授权
  → Research：读取选中项目官方资料，并用 WebSearch 搜索相关讲解
  → 按资料类型分支：文本由 WebFetch 读取；视频原链接交给指定视频解析 Skill
  → Research 汇总功能、特点/创新判断、场景、限制、来源与缺口
  → 关键证据不足则等待用户补充资料、授权补充研究或重新选择
  → Supervisor 校验研究结果及缺口
  → Content 依据研究包生成图文策划
  → Review 审核；初稿后最多自动修改三次
  → 审核通过或转人工处理
  → 人工批准具体策划版本
  → 人工制作图片并上传系统
  → 核对账号、成品图片顺序、标题正文及有效批准；确认预览并点击“发布”
  → 浏览器自动化上传、预览核对并提交发布
  → 核实平台结果；结果不明或需登录/验证时等待人工处理
  → 保存发布记录；必要时人工核实回填
  → 按需手动复盘
```

### 3.2 人工动作必须独立

| 动作           | 授权内容                                                                 | 不代表什么                                   |
| -------------- | ------------------------------------------------------------------------ | -------------------------------------------- |
| 获取热榜       | 按任务配置获取一次热榜快照并展示项目列表                                 | 不代表已经选项目、批准策划或授权发布         |
| 选定并深入研究 | 绑定候选及快照，授权一轮该项目深入研究                                   | 不代表批准任何最终表述或发布                 |
| 授权补充研究   | 针对指定缺口再开展一轮研究                                               | 不得默认为持续研究或无限循环                 |
| 批准策划       | 认可具体策划版本、账号和明确的未解决主观意见                             | 不允许把批准复用于新项目或新版本             |
| 准备成品图片   | 人工制作后上传系统，关联策划版本，确认图片、顺序及制作核对结果           | 不代表批准任意图片或已经授权发布             |
| 点击发布       | 有效批准后确认完整预览，冻结目标账号、实际图片和文案，授权一次浏览器发布 | 不代表提交成功或平台已发布，也不授权改用 API |
| 回填并核实     | 记录平台可观察结果或人工核实事实及核对方式                               | 不把人工结论冒充浏览器自动确认或 API 回执    |

## 4. 第一阶段详细功能需求

### 4.1 任务、候选和项目选择

| 编号   | 功能           | 详细要求与验收                                                                                                                                                          |
| ------ | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1-T01 | 创建任务       | 保存原始要求、创建人、目标账号和可选参考资料；可使用每日 GitHub 热榜解读模板。账号未登记时可先保存草稿，发布前必须绑定有效目标账号                                      |
| P1-T02 | 必要澄清       | 缺少无法推定的关键要求或要求冲突时追问；等待时不继续研究/创作。答复关联原任务，重新判断语义充分性，不以非空直接判定解决                                                 |
| P1-T03 | 列表与详情     | 展示状态、当前阶段、候选快照、选择、研究、策划版本、审核次数、错误、警告及 Trace；保留完整历史                                                                          |
| P1-T04 | 停止与终止     | 停止当前尝试和终止任务分开；在安全位置中止后续工具及生成，拒绝迟到结果。平台提交可能已发生时不能以取消表示未发布，进入结果核实，不承诺自动撤回                          |
| P1-T05 | 人工重试       | 保留失败原因和历史，创建新的执行尝试，不静默覆盖旧候选、选择、研究或内容；既有批准不自动沿用，任务预算不因重试清零                                                      |
| P1-T06 | 中断识别       | 第一阶段不承诺任意步骤自动恢复；异常中断可标记失败，供人工重试。等待人工选择/答复是明确业务等待，不是执行故障                                                           |
| P1-T07 | 热榜候选展示   | 只根据当次有效 API 响应展示项目标识、名称、描述、链接、来源顺序及采集时间；校验和清洗不等于事实核实。选题前不逐个读取 README、不搜索讲解、不生成用途/创新分析或推荐评分 |
| P1-T08 | 选择并授权     | 一次选择一个候选，绑定任务、尝试、候选快照、候选 ID、操作者和时间，原子保存选择及深入研究授权；未选择前不做单项目完整策划                                               |
| P1-T09 | 选择并发与历史 | 防止两人、重复点击或响应丢失造成重复授权/重复研究；旧快照或旧任务版本的选择需拒绝。变更选择保留历史并失效旧下游引用与批准；存在发布锁/结果不明时先核实，不直接改选      |
| P1-T10 | 无候选与不足   | 不固定 API 必须返回多少条，不限定 AI、不按凑数目标加入榜外项目；无可用候选或选中项目证据不足时明确原因并转人工                                                          |

等待人工答复和项目选择期间不持有长时间模型调用或数据库事务；恢复时从持久化上下文开启新的受控调用。相同任务/尝试可包含多个同角色步骤，不能用固定“四角色各运行一次”的表结构限制业务流程。

### 4.2 Agent 职责与工具权限

| 编号   | 角色/能力      | 详细要求                                                                                                                                                                                                                                                                                  |
| ------ | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1-A01 | Supervisor     | 理解任务、必要澄清、组织研究目标和问题、标记核心问题、原生 SDK 分派、等待人工选择、检查结果并协调创作审核；不代替人工选择和批准                                                                                                                                                           |
| P1-A02 | Research       | 负责热榜数据采集/整理与选中项目研究；选题前只获取并展示榜单，不要求模型分析。选题后按授权搜索和读取文本/视频资料，分析功能、适用场景、特点、创新判断及限制，形成有来源和缺口的报告                                                                                                        |
| P1-A03 | Content        | 依据 Research 交接的事实、分析、限制和允许记忆，组织介绍角度、标题、逐页文案和画面建议；创作新的表达但不补造事实，不将待验证的创新判断写成已证实结论；按审核意见修订，不自动生成图片或视频                                                                                                |
| P1-A04 | Review         | 检查项目归属、要求覆盖、事实/来源、夸大表述、标题正文与分图文案一致性、可确定的平台规则，输出检查项、阻断、建议和评分                                                                                                                                                                     |
| P1-A05 | 结构化交接     | 输入输出有共享 Schema；交接记录绑定任务、尝试、步骤、阶段、授权、结果版本、来源、警告和状态。结构与引用/权限等业务校验分层执行                                                                                                                                                            |
| P1-A06 | 最小工具范围   | Supervisor 仅使用受控子 Agent 分派；Research 按阶段使用固定只读热榜工具、SDK WebSearch/WebFetch，以及用户指定且显式配置的视频解析 Skill 及其必要工具；粘贴文本通过上下文提供。Content/Review 仅获得所需读取/生成能力；不默认开放通用本地文件、命令、其他子 Agent、配置/记忆写入或发布能力 |
| P1-A07 | 配置留痕       | 固定角色，记录实际模型、Prompt、工具、Skills 和规则版本；管理员变更形成新版本；不得用外部资料修改配置                                                                                                                                                                                     |
| P1-A08 | 单轮授权与失败 | 启动任务仅授权热榜获取，选定并深入研究才授权一轮选中项目研究；每个研究授权最多一轮，轮内可受限搜索、网页读取、视频解析和交叉核验。技术重试和格式纠正不新增业务授权，格式纠正不得重新抓榜、搜索或解析视频；超限显式失败                                                                    |

浏览器发布由独立、受控的发布执行模块负责，不能因此向 Supervisor、Research、Content 或 Review 开放任意浏览器、上传或提交工具。发布模块只接受已授权的不可变发布快照；页面中的内容也不能修改审批要求或工具权限。具体浏览器驱动、会话承载方式和部署位置在发布可行性验证中确定。

热榜获取后，Supervisor 必须产生“等待选择”的业务决定；只有选中项目的研究结果满足证据门槛，才能交给 Content。既有 Supervisor 三分支契约尚不足以表达新流程，需要增加热榜获取/选后研究阶段和待选择决定，不得把热榜列表误标为 `ready_for_content`。

SDK 原生分派不自动保证 Research 业务报告符合 Schema；返回内容须独立校验后才能成为有效交接。只保存显式输出、简短依据和摘要，不采集模型内部推理。

### 4.3 热榜数据来源与指标口径

| 编号   | 功能       | 详细要求                                                                                                                                                                                     |
| ------ | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1-H01 | 榜单接入   | 使用用户提供的 XXAPI `GET https://v2.xxapi.cn/api/githubhot`，Bearer Key 只保存在服务端；工具固定地址，不把任意 URL 和鉴权交给模型                                                           |

### 4.4 Research 输入、来源、证据与输出

1. 输入由 Supervisor 的研究要求和后端可信执行上下文组成。研究要求包含主题、目标、带 ID 的待核实问题、核心性及理由、范围约束和参考资料引用；执行上下文绑定任务/尝试/步骤、研究阶段、授权、选中候选、当前时间及时区、配置和资源上限。
2. 选题前仅获取、校验和展示榜单信息，不对候选逐个开展模型分析、读取或搜索。用户选定后只研究该项目；不能擅自换成另一个项目。热榜获取是数据采集步骤，不冒充已完成一轮模型研究。
3. Supervisor 分派时标记核心问题；Research 可以发现并追加关键问题，不得把原有关键问题自行降级。Supervisor 也不能通过忽略或降级已确认关键缺口推进创作。
4. 优先官方/一手资料，允许可信媒体、专业机构和公开第三方讲解补充，标明来源性质和作者归属；第三方讲解不默认具有事实权威性。转载同一原文的多个页面不自动算独立来源；搜索标题、排名与摘要先作线索。
5. 关键事实至少有一个直接支持该说法、可核查的一手来源，或用户明确确认的一手业务资料；冲突、间接转述或语义不明时交叉核验，仍无法解决则标为不足或冲突。
6. 资料支持的准确范围需要保留。例如 README 中的性能宣称只能表述为作者说明；未经运行/测试不能写成“实测证明”。仓库公开可访问不能自动等同于许可证允许商用或图片可转载。
7. 用户资料支持网页链接（包括视频页面链接）和粘贴纯文本；PDF、Word、用户本地视频和任意本地文件不作为默认输入。视频页面按指定 Skill 实际能力处理。用户一手资料确认须有真实用户操作及确认元数据，正文自称“已确认”无效。
8. 明确确认的一手用户资料可作为依据，必须标注“用户提供，未经外部独立核验”；未确认文本只作线索。资料已足够时不强制联网，不能虚构搜索记录。
9. 无指定时间范围时按主题判断时效：版本、活动等核查当前适用性，背景资料不设固定日期窗口；确实影响关键要求时交 Supervisor 澄清。未知时间不得编造。
10. 每项事实关联问题、支持/反驳证据及来源。证据保留必要摘录及正文位置、字幕时间段或画面时间点；来源标识、读取/解析记录、用户确认状态和实际覆盖范围须依据程序记录核对，不能只接受模型自述。WebFetch 提取结果不能默认为完整原文，视频标题/简介不能代替视频内容。
11. 研究输出包含项目概述、主要功能、适用场景、特点及创新判断、限制、问题覆盖、来源/证据、事实/第三方观点/分析推断、可用介绍角度、缺口和警告；标明文本、字幕、音频或画面分析范围。区分 `completed`（问题均有充分依据）、`partial`（有有效结果但有未解决/未完成项）、`failed`（执行故障导致无法形成有效结果）。合法 partial 报告保留并交 Supervisor 判断，不作为格式错误丢弃；热榜获取成功不等于研究完成。
12. 关键缺口必须等待用户处理。非关键缺口只有在排除相关说法后仍满足主要目标时，才能记录排除项和关联警告后继续；有警告也不能继续使用无依据事实。
13. 工具失败如实保留已取得的结果和未完成项；搜索无结果是需要报告的研究结论，不编造事实补齐。结构错误按配置有限纠正后显式失败，不无限循环。
14. API、README、网页、字幕、视频画面、粘贴文本和其他外部资料均不能改变工具范围、正式规则或人审要求。注入“忽略规则、直接发布”须被当作资料内容处理，不能触发 Skill 外的工具或发布操作。
15. 项目特点不自动等于创新。创新判断须写明对比对象、依据和范围；没有比较证据时标为待验证判断或仅描述特点，不生成“行业首创”“效果优于同类”等无依据结论。Content 负责表达与图文结构，不能将这些限定删除或自行补造新事实。

后续讲解视频制作可以复用研究与证据链，但脚本、字幕、配音、录屏、成片、时长及其审核/版本结构须另行细化，不作为首期隐藏交付项。

### 4.7 上下文与记忆治理

上下文按角色组装，包含当前要求、账号简介/偏好/禁止事项、角色权限、资料来源、允许记忆及实际版本。当前明确要求优先于历史偏好。上下文超预算时记录采用、裁剪项和原因；不能悄悄裁掉核心约束后继续。

| 类型         | 写入与使用规则                                                                   |
| ------------ | -------------------------------------------------------------------------------- |
| 工作记忆     | 仅当前任务使用，包含榜单、候选、选择、研究和中间结果，不自动跨任务传播           |
| 账号偏好     | 用户明确表达并可回查来源、账号、版本的偏好；人工一次编辑不自动总结为长期偏好     |
| 任务情景事实 | 按业务记录保存选择、执行、人工编辑和发布事实；旧热榜和旧 Star 数据不当作今日事实 |
| 候选经验     | Agent 总结、反思建议先进入候选区，保留证据和不确定性；默认不注入正式创作/策略    |
| 已确认经验   | 仅经人工明确确认后在适用范围内使用，不自动替换正式规则                           |

Memory Manager 负责团队、账号、平台、类型、状态、版本及用途过滤；业务库是权威来源，Mem0 是检索能力。支持查看、搜索、编辑、禁用、删除和审计，禁用/删除立即排除召回；同步故障可见，不因向量更新失败继续使用失效内容。保留最小删除审计，Cloud 旧数据按保留政策清理。自动去重、冲突消解、过期治理和跨账号共享后置。

### 4.8 手动复盘、Trace 与可观测性

- 已结束任务可手动复盘，输入来自候选、选择、研究、内容版本、审核、人工反馈、发布记录和允许记忆；输出证据、可能原因、替代解释、验证建议及不确定性，可存候选经验。
- “审核通过”“用户选定”“人工采用”“发布成功”“内容效果好”分别记录，不能互相代替；复盘失败不改变原业务事实。
- 任务、尝试、步骤、研究授权、候选快照、选择、模型/工具/Skill 调用、记忆、策划版本、审核记录、素材快照和浏览器发布操作可关联回查。
- 同任务可有多个 Trace；记录各轮研究模式、耗时、错误、实际配置、Token 及可获得成本。未知成本标记未知，不伪记为零；避免重复统计。
- 控制台展示摘要及 Langfuse Cloud 链接，Cloud 权限独立配置；不重建完整实验详情平台。
- 上报前排除密钥、登录/平台凭据和不必要个人信息，正文/资料/记忆按已确认数据范围发送。Cloud 故障记录并允许补报，不改变业务状态、不重复研究或发布。
- 首期反思只提出建议，不自动修改 Prompt、正式策略、工具或审批要求。

### 4.9 单 Agent 与多 Agent 对照实验

继续保留第一阶段研究目标，不因平台变化取消。单 Agent 使用相同资料与工具完成研究、策划和自检，多 Agent 使用固定四角色。

1. 冻结榜单及资料快照、研究问题、基础模型、工具范围、审核标准、记忆和预算，记录角色 Prompt 差异。
2. 创作质量对照使用相同的人工选中项目，避免“选了不同项目”混淆协作收益。热榜获取不作为模型分析质量对照；文本/视频资料及分析范围在实验组间一致或明确记录差异，不把用户选择计成模型研究质量。
3. 协作实验统一禁用或使用相同冻结记忆，组间隔离写入；记忆收益实验优先在第二阶段开展。
4. 主指标为人工盲评的要求符合度、事实依据、表达与图文策划完整性；只评系统实际交付物，不把人工成图或视频效果计成模型产出质量。
5. 记录审核通过率、修改量、完成率、耗时、Token、成本、失败样本、评分来源及标准版本；Review 不是唯一裁判。
6. 总体资源上限相同，重复次数、评审人、量表、分歧处理和优势门槛在正式实验前冻结。报告不利案例、限制和无优势结论，不只挑最佳样本。
7. 离线实验不能消耗真实人工发布批准或触发实际上传；保存代码、配置、数据集、评分器和运行标识。固定数据不保证模型逐字一致。

## 6. 第二阶段计划

进入条件：第一阶段热榜获取与选后研究、人工选择、策划审核、素材预览及浏览器发布记录稳定，有可回查案例与评测基线。以下为路线计划，具体参数和上线范围仍需确认。

| 编号  | 模块               | 计划与边界                                                                                                           |
| ----- | ------------------ | -------------------------------------------------------------------------------------------------------------------- |
| P2-01 | 持久化与定时工作流 | 引入 Temporal；支持定时创建/抓榜、选择与审批等待和恢复；实际频率、时区、补跑及去重策略先确认。不能跳过人工选择和批准 |
| P2-02 | 平台指标回流       | 在允许的官方接口或人工导入范围内关联链接、观测时间和可用字段，未知值不当作零；抖音数据权限先验证                     |
| P2-03 | Analytics          | 分析表现、失败和人工修改，区分相关与因果；结果关联数据和计算方式                                                     |
| P2-04 | Strategy           | 基于已验证经验提出候选选题/结构建议，不自动替用户选项目或修改正式策略                                                |
| P2-05 | 记忆与知识治理     | 增加重复/冲突/过期治理、完整账号规范、来源版本和记忆收益实验                                                         |
| P2-06 | 反思与优化验证     | 汇总反馈提出可检验假设，运行受控对照，人工批准后生效，记录基线、回滚目标及证据                                       |
| P2-07 | 评测与工具治理     | 校准裁判、人工分歧、消融和固定回归集；完善工具/Skills 注册、配置版本、上下文预算及证据筛选                           |

定时生成或抓榜不等于定时发布；历史批准不得无限授权后续内容。讲解视频制作为已确认的后续方向，但是否纳入第二阶段、是否自动成片及具体制作链路尚未定，不作为本阶段默认交付。

第三阶段继续以受控策略生效为目标：在人工预设的范围、质量/成本门槛和预算内自动运行验证；只有证据达标的配置才能生效，并保留基线、回滚和停止开关。自动学习不得修改权限、审批制度、准入门槛或扩大发布授权。

| 后续方向      | 追加确认内容                                                                                                        |
| ------------- | ------------------------------------------------------------------------------------------------------------------- |
| 讲解视频      | 脚本、字幕、录屏、素材、配音、剪辑、视频文件、审核和成本；首期图文链路稳定后细化                                    |

| 自定义 Agent  | 可编辑范围、工具组合、权限和实验隔离                                                                                |

| AC-08 | 账号与权限     | 运营人员不能管理成员/工具/凭据；允许自批，未批准或未另行点击发布不能提交，浏览器实际账号不匹配时阻断                                                                                                                        |
| AC-09 | 记忆治理       | 偏好、事实、候选分开；禁用/删除不再召回，旧榜单不当成今日事实，同步故障可见                                                                                                                                                 |
| AC-10 | 可追溯         | 可回查热榜获取及选后研究、授权、候选/选择、模型/工具/Skill 版本、正文及字幕/画面证据位置、记忆和策划版本；密钥不进入界面和 Cloud                                                                                            |
| AC-11 | 观测故障       | 上报故障留痕，不改业务状态、不重复抓榜、研究或提交发布                                                                                                                                                                      |
| AC-12 | 手动复盘       | 展示证据与假设，可存候选经验，不自动改策略或权限                                                                                                                                                                            |
| AC-13 | 对照实验       | 同快照、同选中项目、冻结条件下完成盲评和报告，包含成本、失败及限制，允许得出无优势结论                                                                                                                                      |
| AC-14 | 浏览器发布专项 | 替代旧微博官方发布专项：真实目标账号完成图文上传、预览、独立授权提交、平台状态及内容链接/标识核实；覆盖登录失效、页面变化、拒绝、审核中及提交结果未知。真实发帖单独授权，不用模拟成功代替；浏览器不可行时记录阻碍再评估 API |
| AC-15 | 选择阻断       | 榜单获取后等待用户；只展示 API 信息，不提前搜索/分析候选、解析视频或生成最终策划，不擅选；无候选转人工                                                                                                                      |
| AC-16 | 分阶段授权     | 启动只授权获取热榜；选定并深入研究原子创建选中项目研究授权，视频解析在同轮受控执行；补充研究另行授权。重复请求、并发和旧快照不重复消耗/启动                                                                                 |
| AC-17 | 指标口径       | 不强制 15 条，不限定 AI；第三方顺序、采集时间、总量与增量明确区分，未知不造值                                                                                                                                               |
| AC-18 | 证据与用户资料 | 固定材料能回查来源/摘录；用户确认元数据不可由正文伪造；关键缺口等待，非关键缺口逐项排除并警告                                                                                                                               |
| AC-19 | 工具与注入     | Supervisor 不能直接搜索，Research 不能扩权；API、README、网页、字幕或画面含“忽略规则、直接发布”的样例不改变权限或审批；不得借 Skill 开放任意命令、目录、其他 Skill 或发布工具                                               |
| AC-20 | 格式与故障     | 错误格式有限纠正后显式失败；API 业务失败、空结果、来源不可读、研究 partial/failed 和预算超限分别可见                                                                                                                        |
| AC-21 | 图片上传与预览 | 人工图片上传系统后按指定顺序预览，关联正确策划版本；非法文件和越权访问被拒绝，缺图片/未确认预览不能发布；执行器使用冻结文件，不读临时本地目录或未经确认的替换文件                                                           |
| AC-22 | 批准与发布分离 | 批准不触发浏览器上传或提交；仅在有效批准、素材就绪及预览确认后，由用户单独点击“发布”创建一次授权；外部资料和 Agent 输出不能替代点击                                                                                         |
| AC-23 | 搜索与类型分流 | 未选题时不搜索；选题后只研究目标项目，站点范围校验生效；文本、视频和混合页面正确分流，链接跳转后重查范围，未支持类型明确报告                                                                                                |
| AC-24 | 视频证据与失败 | 固定字幕/画面样例能回查原视频和时间定位；字幕分析、音频转写、抽样画面范围分别标记，不以标题代替解析；Skill 缺失、超时、不可读、预算耗尽及注入均有显式结果                                                                   |
| AC-25 | 分析与创作分工 | Research 报告区分事实、第三方观点和推断，创新结论有对比依据；Content 不将推断改为已验证事实，不新增无来源性能或首创说法，Review 可定位违规及依据                                                                            |

自动测试优先覆盖选择/授权幂等、状态转换、引用归属、版本批准、素材冻结与访问权限、发布防重、预算和记忆过滤。固定工具/页面样例不能替代真实供应商及浏览器联调；真实发布单独验收，本次文档修订不授权发帖。首期不自动生成最终图片，不以图片渲染/视频质量作为 Agent 验收。

### 12.2 已确认实施顺序

1. 修订 PRD，明确本版本与待确认项。
2. 更新共享契约与 Supervisor；完成 Research 独立模块及本地测试。
3. Supervisor + Research 完成后，接入数据库和页面，验收候选 → 人工选择 → 深入研究这段流程；不等四个 Agent 全完成再联调。
4. 接入 Content 的完整图文策划版本，再接 Review 和三轮修改。
5. 接入成品图片上传/排序/预览，迁移人工批准与独立发布授权；完成浏览器发布和结果核实，形成业务闭环。浏览器可行性可提前独立验证，不等待四 Agent 全部完成；无法落地时再评估 API。
6. 完成记忆、观测、复盘和研究评测；后续再细化讲解视频制作、定时，必要时单独确定 API 备选方案。
