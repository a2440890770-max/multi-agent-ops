## 1. 背景、目标与成功定义

### 1.1 背景

项目面向内部运营团队，构建可协作、可追溯、有长期记忆并能够提出和验证改进建议的 Agent 系统。以微博文案运营提供真实任务场景，逐步研究多 Agent 协作、长期记忆、反思和策略优化的实际收益。

### 1.2 目标优先级

1. 验证多 Agent 协作相对单 Agent 的效果。
2. 验证长期记忆的跨任务复用价值。
3. 验证反思与策略优化是否带来可重复的改进。
4. 提升内容产出效率。

系统必须支持获得可信的研究结论。不能将“实验必须得出多 Agent 更优”作为开发验收条件，也不能只凭 Agent 自评证明效果。

### 1.3 三类验收

| 类型     | 第一阶段成功定义                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------------ |
| 功能验收 | 完成任务创建、资料研究、文案生成、审核修改、人工批准、实际发布、记录与人工复盘闭环                           |
| 发布验收 | 人工发布回填可以验证业务流程；官方接口发布需在权限开通后独立验收，未完成时明确标记未验收                     |
| 研究验收 | 完成固定条件下单 Agent 与多 Agent 对照实验，报告质量、修改量、耗时、成本及结论；优势判定门槛在正式实验前冻结 |

“成功发布”不代表内容效果已改善，也不代表系统已经自主进化。首期不以曝光或互动增长作为必须达成的指标。

## 2. 已确认范围与用户权限

### 2.1 第一期边界

- 一个内部团队、一个微博账号；不开发面向外部客户的多租户产品。
- 一次任务产出一条普通微博纯文案，不包含长文章、连续多条、图片及视频。
- 手动创建任务；根据用户指定主题查资料，不主动持续监测热点。
- 固定 Supervisor、Research、Content、Review 四个核心 Agent；另提供手动触发的复盘能力。
- 初稿最多自动修改三轮；之后转人工处理。
- 发布必须人工确认，允许创建者批准自己的内容；批准后立即尝试发布，不支持定时发布。
- 微博发布权限尚未开通，允许临时人工发布并回填链接；不使用未授权接口绕过开放权限。
- 分层记忆采用不同写入规则；候选经验不自动升级为正式策略。
- 第一阶段自主进化限于提出建议，不自动修改提示词、正式策略或工具权限。
- Langfuse 使用官方 Cloud 托管。控制台展示摘要，详细轨迹跳转 Langfuse。
- 账号定位、品牌规范和完整知识治理后续完善，首期只提供基础配置及必要审核规则。

### 2.2 角色权限

| 操作                                         | 管理员           | 运营人员         |
| -------------------------------------------- | ---------------- | ---------------- |
| 登录、查看团队任务与执行记录                 | 是               | 是               |
| 创建、编辑未批准内容、取消任务、发起重试     | 是               | 是               |
| 审批内容、人工发布回填、核实发布结果         | 是               | 是               |
| 手动触发复盘、查看建议                       | 是               | 是               |
| 查看、编辑、禁用、删除业务记忆               | 是               | 是，保留操作记录 |
| 运行已配置的评测实验、提交人工评分           | 是               | 是               |
| 管理成员、账号授权、工具、系统配置和规则版本 | 是               | 否               |
| 直接查看 API 密钥、微博授权凭据              | 不在界面明文展示 | 否               |

所有业务数据在同一团队内共享；后端仍须校验角色。团队账号体系与登录实现方式在技术设计阶段确定。Langfuse Cloud 的成员权限由管理员独立配置，业务角色不自动等同于 Langfuse 权限。

## 4. 第一阶段详细功能需求

以下均为第一阶段范围；微博真实 API 发布受权限前置条件约束，其余核心流程不得依赖权限开通才能开发。

### 4.1 任务创建与管理

**技术栈：React + TypeScript + Vite、Fastify、PostgreSQL。**

| 编号   | 功能         | 详细要求                                                                                                  | 验收要点                                     |
| ------ | ------------ | --------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| P1-T01 | 创建任务     | 手动输入主题/目标、补充要求、参考资料；自动使用团队唯一微博账号。受众、语气等为可选项，缺失时使用基础配置 | 可提交任务，保留原始要求及创建人             |
| P1-T02 | 缺失信息澄清 | 缺少无法合理推定的主题、相互冲突的关键要求时先追问；等待回答期间不继续生成                                | 答复可关联到原任务，未澄清不发布             |
| P1-T03 | 列表与详情   | 展示状态、创建人、时间、当前步骤、最新文案、审核次数、错误及轨迹链接；支持按状态查询                      | 团队成员可查看完整任务历史                   |
| P1-T04 | 取消         | 未进入外部发布请求的任务可取消；运行中在可中止位置停止后续步骤。已发出的发布请求不能靠取消撤回            | 取消后不新发起发布；记录取消人和时间         |
| P1-T05 | 失败重试     | 保留失败原因与历史；人工发起新执行尝试，关联原任务，已有内容不可静默覆盖                                  | 可区分各次执行，旧批准不能用于新版本         |
| P1-T06 | 任务重启处理 | 首期不要求任意步骤恢复；异常中断的执行可标记失败，由人重试                                                | 重启后能识别遗留运行任务，避免永久显示运行中 |

首期不开发任意步骤暂停/继续，不自动重跑整条任务链。模型及只读工具可以进行有限技术重试，次数和超时可配置；发布调用遵循 4.5 的专门规则。

### 4.2 Agent 协作与工具权限

**技术栈：Claude Agent SDK（TypeScript）、Fastify 后台执行器、结构化数据校验。**

| 编号   | 功能         | 详细要求                                                                                                |
| ------ | ------------ | ------------------------------------------------------------------------------------------------------- |
| P1-A01 | Supervisor   | 理解任务、判断是否需澄清、分派研究/创作/审核、处理失败；不代替人工批准发布                              |
| P1-A02 | Research     | 围绕指定主题联网检索及读取用户资料，输出事实摘要、来源链接、可用素材、证据不足项；首期不持续监测热点    |
| P1-A03 | Content      | 根据任务、资料和允许使用的记忆生成一条微博文案；按审核意见修订，保留各版本                              |
| P1-A04 | Review       | 检查任务符合度、事实依据、文案质量及可确定的平台格式要求，输出通过/不通过、具体问题、修改建议及评分     |
| P1-A05 | 结构化交接   | 各 Agent 输出任务标识、版本、结果、来源/依据、警告及状态；格式错误需显式处理                            |
| P1-A06 | 最小工具范围 | Research 获得检索权限；Content 和 Review 仅获得所需读取/生成能力；发布由后端受审批约束的服务执行        |
| P1-A07 | 配置留痕     | 固定角色，管理员可调整配置并形成版本；记录实际模型、提示词、工具与 Skills 版本；不提供任意 Agent 创建器 |

Agent 审核与反思记录仅保存显式输出、判断依据和摘要，不要求采集模型内部推理。检索内容视为外部资料，不得覆盖任务权限、系统约束和发布审批。

### 4.3 上下文、基础规则与知识来源

**技术栈：TypeScript Context Builder、PostgreSQL、Mem0。**

1. 上下文按角色组装，包含任务要求、基础账号信息、允许使用的记忆、资料来源、审核规则、工具权限及版本。
2. 基础配置可填写账号简介、语气偏好和禁止事项；不强制首期建成完整品牌规范系统。
3. 平台格式要求作为可配置规则维护；具体限制以开通接口和账号能力验证结果为准。
4. 资料不足或事实冲突时显式提示，不将无依据推断描述为已确认事实；必要时等待人工补充。
5. 保存实际采用的记忆 ID、版本及资料来源，支持从输出回查依据。上下文过大时按预算裁剪并记录所用项。
6. 完整的知识自动采集、冲突检测、有效期治理及品牌规则编辑工作台放到第二阶段。

### 4.4 审核、修改与人工裁决

**技术栈：Claude Agent SDK、TypeScript 规则校验、React、PostgreSQL。**

- 初稿生成后运行 Review；未通过时最多自动修改三次，每次修改后重新审核。初稿不计入三次修改。
- 第三次修改后仍不通过，进入“待人工处理”，停止自动生成及发布。
- 人工可编辑并重新审核、调整要求发起新执行、或终止任务；不通过重试静默重置当前执行的修改计数。
- 格式、字数及权限等确定性阻断必须满足。主观质量分歧可由人工裁决，记录裁决理由和未采纳意见。
- 事实证据不足不能因模型给出高分而视为事实已验证；人工需补充依据、修改表述或明确处理该风险。
- 人工编辑后重新进行基础校验与必要审核；未经授权的自动修改不得覆盖人工编辑版本。
- “审核通过”和“人工批准发布”分离；批准绑定内容版本、内容摘要、账号、批准人及时间。文案变更立即使原批准失效。

### 4.5 微博发布与异常处理

**技术栈：TypeScript 发布适配器、微博官方 API 或官方工具、PostgreSQL；具体接口在权限验证后确定。**

| 编号   | 功能           | 详细要求及验收                                                                                                                 |
| ------ | -------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| P1-P01 | 权限验证       | 管理员完成开发者认证、服务开通与账号授权验证；记录接口可用性、费用及限额。未验证前不宣称已具备 API 发布能力                    |
| P1-P02 | 发布批准       | 管理员或运营人员可批准自己或他人任务；后端校验角色、当前内容版本、账号、基础规则及取消状态                                     |
| P1-P03 | 官方发布       | 有效批准后立即尝试发布，记录调用标识、内容版本、结果及平台内容 ID/链接；首期不支持定时发布                                     |
| P1-P04 | 临时人工发布   | 权限未开通时，审批后进入待人工发布；用户复制批准版本到微博发布并回填链接，记录操作人与方式。明确区分人工确认成功和接口确认成功 |
| P1-P05 | 防重复         | 同一发布版本建立唯一发布操作标识并防并发提交；任务重试不自动重发已成功内容                                                     |
| P1-P06 | 待核实         | 超时、连接中断等导致结果未知时，进入“发布待核实”，禁止盲目自动重试；可通过官方查询能力或人工查账号确认                         |
| P1-P07 | 核实与重试     | 查明成功则回填平台标识；确认未发布才允许有权限人员重试，并重新检查批准有效性；仍不确定则保持待核实                             |
| P1-P08 | 取消及撤回边界 | 发送前可取消；发送后不保证撤销。首期不提供自动删帖、撤回或发布后编辑能力                                                       |

模拟适配器仅用于开发测试，不计为真实发布。首次闭环以成功发布内容为目标，阅读量、互动量采集不作为第一阶段必验条件。

### 4.6 分层记忆及写入治理

**技术栈：Mem0、自研 TypeScript Memory Manager、PostgreSQL；Mem0 的嵌入模型与检索存储配置在技术设计中确定。**

| 层级/类型           | 首期内容与写入方式                                         | 后续任务是否可直接使用                            |
| ------------------- | ---------------------------------------------------------- | ------------------------------------------------- |
| 工作记忆            | 当前任务上下文、中间结果；按任务隔离                       | 仅当前任务使用，不自动跨任务传播                  |
| 语义记忆：账号偏好  | 用户明确表达的偏好，保留来源、账号与版本；人工修改可更新   | 有效状态可使用；当前明确任务要求优先于历史偏好    |
| 情景记忆：任务事实  | 实际执行、人工修改和发布结果，依据业务记录保存             | 可检索相关事实，不能据此自动推导通用策略          |
| 候选经验            | 成功经验和 Agent 总结先入候选区，记录证据和不确定性        | 默认不注入正式创作/策略上下文；仅供复盘和实验读取 |
| 已确认经验/策略记忆 | 首期仅经人工明确确认的经验可启用，正式策略不由反思自动变更 | 在明确适用范围内使用，记录确认人和依据            |

具体规则：

1. 人工修改意见保留原文案、修改后文案及可选理由；未经明确确认，不把一次编辑自动概括为长期偏好。
2. “审核通过”“人工采用”“发布成功”和“运营效果好”分别记录；发布成功不自动证明经验有效。
3. 所有长期记忆包含团队、账号、类型、来源任务/输入、状态、版本、创建/更新时间和确认依据。
4. 支持查看、搜索、编辑、禁用及删除；删除/禁用后不得继续检索使用。Mem0 与业务记录变更需有同步状态和失败提示。
5. 删除保留最小操作审计，不继续以普通检索方式暴露已删除记忆正文；Cloud 既有日志清理遵循另行确定的保留政策。
6. 按团队、账号、状态及角色用途过滤，首期不跨账号共享；任务事实和原始产出以业务数据库为准，Mem0 提供检索能力。
7. 完整自动去重、矛盾消解和过期治理后置；首期冲突项可人工禁用，不自动覆盖已确认规则。

### 4.7 手动反思与改进建议

**技术栈：Claude Agent SDK（TypeScript）、PostgreSQL、Langfuse Cloud；首期不强制单独部署 Python 反思服务。**

- 已结束任务（成功、失败、终止）可由用户手动触发复盘；不定时自动执行。
- 输入来自任务记录、审核与修改历史、明确人工反馈、可获得的 Langfuse 评分/轨迹及相关记忆。
- 输出包含问题/经验、关联证据、可能原因、替代解释、改进假设、建议验证方法及不确定性。
- 在任务详情展示，允许保存为候选经验。区分“有证据支持的事实”与“模型推测的原因”。
- 不自动修改提示词、规则、正式策略或工具权限；管理员依据建议手动调整配置仍需形成版本。
- 反思失败不改变原任务发布结果，可单独重试。

### 4.8 可观测性与评测基础设施（对应初稿 4.9）

**技术栈：OpenTelemetry、Langfuse Cloud、TypeScript SDK、PostgreSQL。**

本模块负责采集、汇总、展示及实验记录。Langfuse 是本模块的基础平台；反思模块解释问题和提出假设，策略优化模块设计实验并决策，工作流模块执行和恢复，职责不互相替代。

1. 业务任务、执行尝试、Agent 步骤、模型调用、工具调用、记忆检索、上下文构建和审核通过标识关联；使用任务 ID 与尝试 ID 回查。
2. 同次执行的步骤组成关联轨迹；重试或长流程可以关联多条 Trace，不以“一任务必须只有一条 Trace”限制实现。
3. 记录耗时、错误、模型及提示词版本、记忆使用情况、Token 和可获得的成本；无法获取的成本标记未知，不伪记为零。
4. 统一自动与手动埋点，避免一次模型或工具调用重复统计。
5. 代码检查、Review、模型裁判、人工盲评、运营采用反馈分别保存评分对象、来源、标准版本、值与说明。
6. 控制台展示任务级摘要及 Langfuse 链接；用户需具备相应 Cloud 访问权限。业务权限不能仅依靠隐藏前端链接实现。
7. 业务数据库保存任务与审批事实；Cloud 不可用时记录上报失败并允许补报，不使已批准发布因观测上报故障而被反复执行。
8. 发送前脱敏，排除平台令牌、模型密钥、登录凭据及不必要个人信息；正文、来源和记忆内容按团队确认的数据范围发送。
9. Langfuse Cloud 用于执行轨迹和评测，不代替业务日志、数据库备份、任务调度或正式记忆库。

**技术栈：TypeScript 实验执行器、Claude Agent SDK、Langfuse Cloud 数据集/实验/评分；统计分析可使用 Python + pandas + NumPy。**

| 项目       | 第一阶段要求                                                                                              |
| ---------- | --------------------------------------------------------------------------------------------------------- |

| 发布隔离   | 离线实验不调用真实发布；实验发布工具使用模拟实现，不能消耗业务发布批准                                    |

| 运行控制   | 记录随机性、重复运行计划、成本预算及失败样本；不能只保留成功结果或挑选最佳输出                            |

历史失败案例须经整理和人工确认后入集；开放创作案例可保存要求与评分标准，不必强制唯一参考文案。首期必须具备基本记忆写入/检索，但不要求同时完成完整的记忆收益实验，后者优先安排在第二阶段。

## 5. 流程与状态设计

### 5.1 主流程

手动创建 → 信息澄清（必要时）→ 资料研究与上下文构建 → 文案生成 → Review → 自动修改（最多三轮）→ 审核通过或人工处理 → 人工批准具体版本 → 官方接口发布或临时人工发布 → 确认结果 → 记录并可手动复盘。

### 5.2 状态分离

| 维度     | 状态                                                       | 说明                                           |
| -------- | ---------------------------------------------------------- | ---------------------------------------------- |
| 执行状态 | 待澄清、排队中、执行中、待人工处理、产出就绪、失败、已取消 | 描述生成与审核过程，失败记录具体步骤           |
| 审批状态 | 未申请、待批准、已批准、已失效                             | 绑定内容版本；修改或新执行使旧批准失效         |
| 发布状态 | 未发布、待人工发布、发布中、发布待核实、已发布、发布失败   | 已发布区分人工回填与接口确认；终态保留确认方式 |
| 复盘状态 | 未触发、处理中、已完成、失败                               | 与任务及发布结果独立                           |

批准只允许在基础检查通过、无未解决阻断且内容版本稳定时进行。服务端通过版本检查防止两人同时编辑或审批导致旧内容被发布。发布待核实期间不得创建同版本的新发布请求；人工回填应核对账号和批准版本，发现差异需显式记录，不能假定所发内容与批准内容一致。

### 8.2 数据权威来源与模块分工

- PostgreSQL：业务任务状态、内容版本、审批、发布结果、正式配置、记忆治理元数据和审计的权威来源。
- Mem0：长期记忆提取、检索及更新能力；由 Memory Manager 控制写入、状态和适用范围，不承担审批授权。
- Langfuse Cloud：执行轨迹、评分、固定测试集和实验运行记录；业务库仅存必要标识及摘要，不另造第二套实验详情平台。
- Reflection Engine：分析证据，输出经验和假设；不负责最终证明有效或直接修改正式策略。
- Strategy Optimizer：设计验证、分析效果及管理策略生效和回滚。
- Temporal：第二阶段起负责工作流运行和恢复；不代替业务授权与平台侧防重核查。

### 9.2 后端能力边界

首期提供任务创建与澄清、状态查询、取消与重试、内容版本编辑、审核与裁决、批准与失效、发布及回填核实、记忆治理、复盘、评测入口、成员与配置管理能力。接口路径、请求结构、错误码和数据库物理模型在技术设计中确定，不在本文伪装为已验证实现。

所有修改操作须服务端校验权限和目标版本；发布、审批和记忆更新应保留审计记录。

## 11. 第一阶段验收清单

| 编号  | 场景         | 验收结果                                                                          |
| ----- | ------------ | --------------------------------------------------------------------------------- |
| AC-01 | 正常任务     | 能从手动输入完成研究、生成、审核、批准与真实发布记录；临时人工发布明确标记方式    |
| AC-02 | 信息不足     | 进入澄清等待，回答后继续；不自行构造关键业务要求                                  |
| AC-03 | 连续审核失败 | 初稿后最多自动修改三次；仍不通过转人工，无无限循环                                |
| AC-04 | 人工处理     | 可编辑重审、裁决主观分歧、重启或终止；确定性阻断不能绕过                          |
| AC-05 | 批准失效     | 批准后编辑文案，旧批准失效，发布服务拒绝旧版本请求                                |
| AC-06 | 发布防重     | 重复点击、并发提交、超时或进程中断不导致自动重复发布；结果未知进入待核实          |
| AC-07 | 取消与失败   | 取消阻止后续发布；失败可查原因、人工重试留痕；取消不假装撤回已发内容              |
| AC-08 | 账号与权限   | 运营人员不能管理密钥/成员/工具配置；允许对自己内容审批；无授权不得调用发布        |
| AC-09 | 记忆治理     | 偏好/事实/候选分开；候选不直接用于正式策略；禁用/删除不再召回；同步失败可见       |
| AC-10 | 轨迹与评分   | 任务能回查 Agent、工具、记忆与内容版本；评分来源可分辨；密钥不出现在 Cloud/界面   |
| AC-11 | 观测故障     | Cloud 上报故障有记录，不篡改业务状态、不重发微博                                  |
| AC-12 | 手动反思     | 展示证据和假设，可存候选经验；不自动修改策略和权限                                |
| AC-13 | 对照实验     | 单/多 Agent 在冻结条件下完成离线实验和人工盲评，报告失败样本、质量、成本及限制    |
| AC-14 | 官方发布专项 | 权限开通后，以批准版本通过官方接口/工具真实发布并核对结果；未开通则该项保留未验收 |

自动测试优先覆盖审批失效、发布防重、状态转换、权限和记忆过滤等易回归行为；真实接口权限与内容可见性另做受控人工联调。实验数据不能触发实际账号发布。

## 12. 两人协作与 GitHub 进度管理

### 12.1 协作方式

- 以 GitHub Issue 承接需求，关联本文需求编号、阶段、完成条件和依赖。
- 使用短期分支和 PR，代码改动关联 Issue；合并前由另一人审阅关键权限、发布和数据变更。
- 使用里程碑或项目看板跟踪“待开发、开发中、待验证、受阻、完成”，不以提交次数代替完成度。
- PR 至少说明行为变化及验证结果。基础 CI 覆盖类型检查、构建和必要测试；模型实验按预算手动触发，避免每次提交产生不可控费用。
- 文档、配置示例、实验结果摘要与代码版本关联；凭据和敏感任务原文不得提交到仓库。
- 无固定交付时间，采用完成条件驱动里程碑。实际人员分工由团队确认，建议一人侧重后端/Agent/发布，一人侧重控制台/记忆/评测，接口和关键流程共同评审。

### 12.2 第一阶段建议里程碑

| 里程碑                | 主要交付                                                       | 依赖与退出条件                                        |
| --------------------- | -------------------------------------------------------------- | ----------------------------------------------------- |
| M0 外部能力验证       | 微博权限申请与发布验证计划、模型/记忆/Cloud 接通、小型技术验证 | 明确可用与受阻能力，不以申请提交视为权限开通          |
| M1 任务与人工流程     | 登录、角色、任务状态、内容版本、审批、人工发布回填             | 可走通不依赖 Agent 的人工业务骨架                     |
| M2 Agent 与记忆       | 四 Agent、三轮修改、基础上下文、分层记忆、取消和失败处理       | 固定样例能完成生成到审批，候选经验不越权              |
| M3 追踪与复盘         | Langfuse 摘要/链接、评分、手动反思                             | 有可回查证据链并能应对上报失败                        |
